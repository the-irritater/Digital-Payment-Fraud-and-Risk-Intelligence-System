| Metadata | Details |
| :--- | :--- |
| **Author** | Sanman Kadam |

| **Objective** | Binary classification: fraudulent (1) vs legitimate (0) digital payment transactions |
| **Primary Metric** | PR-AUC (Average Precision) |
| **Secondary Metrics** | ROC-AUC, Precision, Recall, F1, Expected Financial Loss, Brier Score, ECE |

## Model Overview

This model predicts the probability that a digital payment transaction is fraudulent. It is optimized for precision-recall tradeoffs in highly imbalanced datasets, with probability calibration via Platt scaling and cost-sensitive threshold selection.

## Training Data

| Field | Value |
| :--- | :--- |
| **Source** | [PaySim Synthetic Financial Dataset](https://www.kaggle.com/datasets/ealaxi/paysim1) (Kaggle) |
| **Nature** | Synthetic mobile-money transactions generated by the PaySim simulator |
| **Size** | 6.36 million transactions total; 400,000 sampled for training |
| **Filtered Types** | `TRANSFER` and `CASH_OUT` only (PaySim fraud labels are concentrated in these types) |
| **Target Column** | `isFraud` (0 = legitimate, 1 = fraudulent) |
| **Class Imbalance** | ~0.2% fraud rate in filtered training set |

### Split Strategy

Strict **temporal split** based on the `step` column (no shuffling):

| Split | Proportion | Purpose |
| :--- | :--- | :--- |
| Training | 70% | Model fitting |
| Validation | 15% | Hyperparameter tuning, threshold selection, calibration fitting |
| Test | 15% | Final one-time evaluation (untouched during training) |

### Methodology Safeguards

1. **Threshold selection** is locked on the Validation set. The test set is never used for model decisions.
2. **Probability calibration** via `CalibratedClassifierCV` (Platt/sigmoid scaling) fitted on the Validation set.
3. **Temporal ordering** ensures no future information leaks into training features.

## Feature Engineering

All features use **strictly causal (backward-looking) construction**. For any transaction at time T, only information from times before T is used.

| Feature | Description | Leakage Risk |
| :--- | :--- | :--- |
| `log_amount` | Log-transformed transaction amount | None (same-row) |
| `hour_of_day` / `is_night_time` | Temporal cycle features from step | None (same-row) |
| `type_*` | One-hot encoded transaction type | None (same-row) |
| `amount_to_orig_prior_mean_ratio` | Current amount / customer's prior expanding mean | Mitigated: causal expanding window excluding current row |
| `transactions_last_1h/6h/24h` | Backward-looking rolling count via `searchsorted` | Mitigated: proper rolling window on sorted customer history |
| `amount_velocity_6h` | Total amount in prior 6-hour window | Mitigated: backward-looking cumsum |
| `is_new_beneficiary` | First occurrence of (originator, destination) pair | Mitigated: uses cumcount |
| `orig_balance_err` / `dest_balance_err` | Discrepancy between expected and actual post-tx balance | **Known PaySim artifact** (see ablation study) |

### Cost-Optimized Threshold Selection

The decision threshold is selected on the **Validation set** by minimizing total expected financial loss:

$$\text{Loss} = \sum_{\text{each missed fraud}} \text{actual\_amount}_i + (\text{FP count} \times \text{INR } 200)$$

At the cost-optimized threshold, the model achieves high recall at the expense of lower precision. This is a deliberate operating-point choice appropriate for fraud detection, where missing a fraud (false negative) is far more costly than investigating a legitimate transaction (false positive).

## Known Limitations

1. **Synthetic training data**: The model is trained on PaySim simulation data, not real bank transactions.
2. **No real UPI data**: This model has not been validated against actual Indian UPI transaction distributions.
3. **Balance field artifacts**: PaySim cancels fraudulent transactions in the simulation, creating unrealistic balance patterns. The ablation study quantifies this dependency.
4. **Single dataset generalization**: Performance metrics reflect this specific PaySim dataset split.
5. **Risk score is not probability**: The composite risk score (0-100) produced by the Risk Engine is a weighted heuristic, not a calibrated probability.

## Intended Use

This model is intended as a **portfolio demonstration** of an end-to-end fraud detection pipeline. It is not intended for deployment in a production payment system without:

- Training on real, representative transaction data
- Regulatory compliance review
- Adversarial robustness testing
- Continuous monitoring and retraining infrastructure
- A/B testing against existing fraud systems

## Ethical Considerations

- The model makes no decisions based on protected demographic attributes.
- False positive impacts should be weighed against false negative costs using the cost-sensitive threshold framework provided.
- Any deployment should include human-in-the-loop review for high-risk decisions.
